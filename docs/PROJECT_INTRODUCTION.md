# 基于 MCP 的本地工具服务实践：数据库操作与 Markdown 文档协同平台

## 1. 项目简介

这是一个面向 AI 工具调用场景的本地服务化项目，目标是把数据库操作、协议接入和 Markdown 文档协同能力整合到统一入口中，降低研发过程中的上下文切换成本。

当前有效实现基于 Spring Boot 和 Java 17，既提供适合 AI 客户端集成的 MCP / HTTP 工具接口，也提供一个面向本地知识文档的 Markdown 预览工作台。

## 2. 解决的问题

在 AI 辅助研发和本地工程协作场景中，通常会同时出现几类需求：

- 对关系型数据库执行查询、更新和结构查看
- 通过统一协议把工具能力暴露给 AI 客户端
- 浏览本地 Markdown 文档，并在文档上下文中直接做接口调试

如果这些能力分散在多个脚本、多个服务或多个页面里，使用成本和维护成本都会迅速上升。这个项目的核心目标，就是把这些动作收敛到统一服务中。

## 3. 当前有效架构

当前真实运行链路采用单体服务架构：

- 后端框架：Spring Boot 3.x
- 运行时：Java 17
- 数据访问：JDBC + 多数据源/动态数据源
- 协议层：MCP 兼容的 JSON-RPC 与 HTTP 接口
- 页面层：服务端返回的 Markdown 预览工作台
- 资源层：关系型数据库与本地 Markdown 文件系统

整体分层可以概括为：

- 接入层
  - 健康检查
  - MCP / HTTP 接口
  - Markdown 页面接口
- 工具层
  - 数据库工具
  - Markdown 工具
- 服务层
  - SQL 执行服务
  - 查询历史服务
  - Markdown 预览与缓存逻辑

## 4. 核心能力

### 4.1 数据库工具能力

项目提供了一组面向数据库操作的统一接口，支持：

- 查询语句执行
- 更新与 DDL 执行
- 按 SQL 语义自动判断执行类型
- 表清单查询
- 表结构查询
- 查询历史记录检索与清理

这类能力既可以通过普通 HTTP 接口使用，也可以通过 MCP 工具方式暴露给 AI 客户端。

### 4.2 MCP 协议能力

项目内部实现了一层轻量的 MCP 协议处理逻辑，支持：

- 服务初始化
- 工具列表枚举
- 工具调用
- 资源列表与资源模板描述
- JSON-RPC 风格的统一响应结构

这样做的意义在于，工具能力不再直接绑定某个单独页面或脚本，而是能够被兼容 MCP 的客户端按标准方式接入。

### 4.3 Markdown 预览工作台

除了工具接口，项目还提供了一套一页式 Markdown 工作台，用于本地文档浏览和联动调试。当前页面支持：

- 文件树浏览与搜索
- 多标签页切换
- 面包屑与标题树联动
- Markdown 预览与原文切换
- 文档下载与保存
- 从文档提取接口信息并注入请求调试面板

这使页面不只是“文档查看器”，而是一个面向研发场景的文档协同工作台。

## 5. 性能与稳定性实践

为了降低文档切换时的卡顿与闪烁，当前实现做了几项关键优化：

- 把页面加载拆成“侧栏壳层加载”和“文档内容加载”
- 在后端增加侧栏缓存与文档缓存
- 用文件元信息校验缓存有效性，尽量兼顾性能和实时性
- 在前端使用并发保护，避免快速切换时旧请求覆盖新状态
- 把代码高亮、原文加载、tooltip 初始化等逻辑改成局部执行

在交互一致性方面，页面还保持了以下设计：

- 标签切换与关闭走页内更新，不做整页跳转
- 预览与原文切换尽量保持阅读位置连续
- 树展开状态、标签状态、调试面板状态等保存在浏览器本地

## 6. 工程化设计

### 6.1 配置治理

项目采用模块化配置方式，支持外部配置覆盖默认配置，便于在不同环境下切换运行参数。

同时，Markdown 工作目录采用了持久化配置和回退策略，保证页面在配置失效时仍能进入可用状态。

### 6.2 可维护性

为保证维护成本可控，项目当前实现具备以下基础能力：

- 健康检查接口
- 查询历史记录
- 统一异常响应
- 配置与功能开关分离
- Markdown 页面与数据库工具模块分层

这些设计让项目既能作为本地研发工具，也保留了继续演进的空间。

## 7. 适用场景

这个项目适合以下类型的使用场景：

- AI 辅助开发中的数据库操作与结果分析
- 本地知识库或接口文档的结构化浏览
- 文档驱动的接口联调与回归验证
- 需要把“工具调用 + 文档上下文”整合到一起的研发团队

## 8. 工程经验总结

从工程视角看，这个项目有两个值得强调的点。

第一，工具能力、协议能力和页面能力不是割裂实现，而是通过统一服务组织起来的。这种方式更适合被 AI 客户端消费，也更适合后续扩展。

第二，在仓库中存在多条历史技术路线时，必须明确“当前真实运行链路”。只有把主链路和历史原型区分清楚，文档、维护和后续演进才不会持续失真。
